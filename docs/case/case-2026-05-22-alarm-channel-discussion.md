# GB28181 告警通道机制分析与最佳实践

> 日期: 2026-05-22 | 涉及设备: 35020000201311000070 (DSJ_V8), 35020000201311095331 (5G摄像头) | 涉及服务: wvp, jxt-frontend

## 1. 背景

在 GB28181 视频监控系统中，设备报警上报后需要在平台端展示报警信息、抓拍快照、支持录像回放。实际对接中发现，不同厂家的终端设备对告警通道的支持程度不同，导致报警数据入库后可能出现无通道编号、无快照、无法回放等问题。

本文档基于两次实际对接排查，整理了 GB28181 协议中告警通道的规定、行业主流平台的做法、以及 WVP 平台的改进方案。

## 2. GB28181 协议中关于告警通道的规定

### 2.1 20 位国标编码规则

20 位编码中第 11-13 位为**类型编码**，决定了该编码代表什么类型的设备或通道：

| 类型编码 | 含义 | 说明 |
|---------|------|------|
| 111 | 编码设备 | DVR/NVR 等后端录像设备 |
| 131 | 视频通道 | IPC 摄像头的视频流通道 |
| 132 | 报警通道（部分标准） | 报警输入通道 |
| 134 | 报警输入设备 | 红外、烟感、门禁等报警输入 |
| 136 | 语音输入通道 | |
| 137 | 语音输出通道 | |

来源：GB/T 28181-2016 附录 D 表 D.1

### 2.2 报警通知中的 DeviceID

根据 GB/T 28181-2016 第 9.4 节，报警通知命令采用 MESSAGE 方法，XML 中的 `DeviceID` 标识**产生报警的设备或通道**。

从实际 SIP 抓包来看（参考 [CSDN 示例](https://blog.csdn.net/qq_38795209/article/details/111245251)）：

```
报警订阅 (SUBSCRIBE):  目标是设备编码 (类型 111)
布防 (SetGuard):       XML DeviceID 是视频通道编码 (类型 131)
报警通知 (NOTIFY):     XML DeviceID 是视频通道编码 (类型 131)
```

报警通知示例：

```xml
<Notify>
  <CmdType>Alarm</CmdType>
  <SN>1288</SN>
  <DeviceID>34020000001310000001</DeviceID>   <!-- 视频通道编码，类型 131 -->
  <AlarmPriority>4</AlarmPriority>
  <AlarmMethod>5</AlarmMethod>
  <AlarmTime>2020-12-14T09:58:30</AlarmTime>
  <Info>
    <AlarmType>2</AlarmType>
  </Info>
</Notify>
```

### 2.3 关键结论

- 协议规定报警通知的 `DeviceID` 应为**产生报警的通道编码**
- 对于多通道设备（NVR），`DeviceID` 应为具体的视频通道或报警输入通道
- 对于单通道设备（执法记录仪、IPC），`DeviceID` 可能是设备自身编码
- 类型编码 134 专门用于报警输入通道，但不是所有设备都支持

## 3. 行业主流平台的做法

### 3.1 海康威视

- 设备端需**启用事件功能**（移动侦测、视频遮挡等），否则订阅后收不到报警
- 需要**通道布防**（SetGuard）针对具体视频通道编码
- 支持**报警输入通道**（类型 134）的独立配置
- 平台端对找不到通道的报警做 fallback 处理，关联到父设备保存

参考：[海康威视 IPC/NVR 国标配置介绍](https://zhuanlan.zhihu.com/p/476745458)

### 3.2 大华

- 基本流程与海康一致
- 支持 GB28181 目录查询中包含报警通道
- 部分型号需要手动在设备 Web 端配置报警通道的国标编码

### 3.3 通用做法总结

| 平台 | 处理方式 |
|------|---------|
| 海康 | 支持报警输入通道(134)，无通道时 fallback 到父设备 |
| 大华 | 支持报警输入通道(134)，目录中包含报警通道 |
| LiveGBS | 需手动配置摄像头报警通道 ID，类型编码 134 |
| EasyCVR | 需启用事件功能 + 通道布防，支持报警输入通道 |

参考：
- [LiveGBS 报警配置](https://blog.csdn.net/qq_41979241/article/details/124728934)
- [EasyCVR 海康设备接入](https://www.cnblogs.com/easycvr/p/16525594.html)

## 4. 实际对接案例分析

### 4.1 案例 1：DSJ_V8 执法记录仪（35020000201311000070）

**设备特征**：单通道设备，编码类型 131（视频通道），设备编码即通道编码。

**问题**：终端未配置告警通道时，报警通知 DeviceID 为设备自身编码 `35020000201311000070`，设备目录只上报了一个子通道 `uni0110011122110841240405`，导致 WVP 在 `wvp_device_channel` 表中找不到匹配的通道记录，报警被静默丢弃。

**解决**：在终端配置告警通道后，设备目录从 1 个通道变为 2 个通道（多了 `35020000201311000070` 自身），报警成功入库。

```
配置前: Catalog 返回 1个，1/1  → 只有 uni0110011122110841240405
配置后: Catalog 返回 1个，1/2 + 1个，2/2  → 新增 35020000201311000070
```

**WVP 代码改进**：修改 `AlarmServiceImpl`，当找不到通道时仍保存报警记录，不再静默丢弃。

### 4.2 案例 2：5G 摄像头（35020000201311095331）

**设备特征**：多通道设备，拥有视频通道（131）和报警通道（134）。

**问题**：设备上报报警时 DeviceID 为报警通道 `35020000201341005331`（类型 134），但设备目录只上报了视频通道 `35020000201311005331`（类型 131），报警通道未包含在目录中。导致：

| 报警阶段 | 报警 DeviceID | 通道查找结果 | channel_id |
|---------|-------------|------------|-----------|
| 未配置告警通道 | 空 | 未找到 | 0 |
| 配置后首次报警 | `35020000201341005331` (134) | 未找到（目录不含此通道） | 0 |
| 设备重新同步目录后 | `35020000201341005331` (134) | 找到（临时创建，id=10） | 10 |
| 设备离线后 | - | channel_id=10 被清理 | 无效 |

**根本原因**：

1. 设备目录(Catalog)响应中**不包含报警通道**（只包含视频通道）
2. 报警通道仅在设备在线期间临时存在，设备离线后被清理
3. 报警关联到告警通道而非视频通道，导致回放和快照依赖一个不稳定的通道

## 5. 报警通道 vs 视频通道的对比

| 维度 | 视频通道（131） | 报警输入通道（134） |
|------|---------------|------------------|
| 目录可见 | 始终出现在 Catalog 中 | 部分设备不包含在 Catalog 中 |
| 生命周期 | 设备注册后持续存在 | 可能随设备离线被清理 |
| 视频能力 | 可拉流、可回放、可抓拍 | 通常无视频流 |
| 报警关联 | 可用于回放和快照 | 仅标识报警来源 |
| 稳定性 | 高 | 取决于设备实现 |

## 6. 改进方案

### 6.1 已实施：报警不再静默丢弃

修改 `AlarmServiceImpl.onApplicationEvent()`，当找不到匹配通道时仍保存报警记录：

```java
if (deviceChannel == null) {
    log.warn("[报警] 未找到通道 {}/{}，仍保存报警记录", notify.getDeviceId(), notify.getChannelId());
    alarm.setSnapPath(null);
} else {
    alarm.setChannelId(deviceChannel.getId());
    alarm.setSnapPath("snap/alarm_" + notify.getChannelId() + "_" + System.currentTimeMillis() + ".jpg");
}
alarmQueue.offer(alarm);
```

### 6.2 建议改进：报警关联到视频通道

当前报警直接使用告警通道（134）的 ID 关联，但告警通道不稳定。建议增加 fallback 逻辑：

```
报警查找通道的优先级：
1. 精确匹配：使用报警 DeviceID 查找对应通道
2. 同设备 fallback：找不到时，使用同设备的视频通道（131）
3. 无通道保存：都没有时，channel_id 置空，仅保存报警记录
```

这样可以确保：
- 有告警通道时，精确关联
- 告警通道不存在或已清理时，回退到视频通道，仍可抓拍和回放
- 即使没有任何通道，报警也不丢失

### 6.3 建议改进：前端展示

对于 `channel_id=0` 的报警，前端应：
- 快照列显示"无通道，无法抓拍"
- 回放按钮置灰或提示"无关联视频通道"
- 报警基本信息（类型、时间、经纬度）仍正常展示

## 7. 终端配置建议

针对不同类型的设备，推荐的告警配置方式：

### 7.1 单通道设备（执法记录仪、单 IPC）

- **必须**：确保 Catalog 目录响应中包含设备自身编码作为通道
- **可选**：配置独立的报警输入通道（类型 134）
- 如果设备自身编码类型为 131（视频通道），报警 DeviceID 使用设备编码即可

### 7.2 多通道设备（NVR、多通道 IPC）

- **推荐**：在设备端配置报警输入通道，类型编码使用 134
- **必须**：确保 Catalog 目录响应中包含所有通道（包括报警通道）
- 报警 DeviceID 应使用具体的报警通道编码

### 7.3 通用要求

1. 设备端必须**启用事件功能**（移动侦测、视频遮挡等）
2. 平台端必须发送**报警订阅**（SUBSCRIBE Alarm）
3. 平台端可选择性发送**布防命令**（SetGuard）
4. 报警订阅有有效期，到期需自动续期
